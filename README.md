## Лабораторная работа №10 — Добавление рассылки в очередь задач

1. Миграция `2026_11_19_000005_create_jobs_table.php` создаёт `jobs` и `failed_jobs`.
2. `QUEUE_CONNECTION=database` установлен в локальном `.env.example`.
3. Создано задание `app/Jobs/VeryLongJob.php`.
4. В `NewsController::store()` вместо немедленной отправки вызывается `VeryLongJob::dispatch($article->id)`. Сама отправка через `ArticleCreatedMail` выполняется в методе `handle()`.
5. Работник запускается `php artisan queue:work database --tries=3 --sleep=1`.
6. После создания новости задача появляется в `jobs`, а после обработки письмо фиксируется в `storage/logs/laravel.log`, если используется `MAIL_MAILER=log`. Для настоящего email нужен SMTP.

### Локальная установка для преподавателя (без хостинга)

Требуется PHP **8.3+** (pdo_sqlite, mbstring, openssl, fileinfo), Composer или готовая папка `vendor`.

```bash
composer install
php scripts/setup-local.php
```

**Первый терминал:**

```bash
php artisan serve --host=127.0.0.1 --port=8000
```

**Второй терминал:**

```bash
php artisan queue:work database --tries=3 --sleep=1
```

Откройте http://127.0.0.1:8000. Учётные данные локального модератора автоматически записываются в `LOCAL_LOGIN.txt` (не публикуется в Git). Можно запустить всё сразу через `START_MAC.command` или `START_WINDOWS.bat`.

Для демонстрации постановки задачи в очередь **сначала остановите worker**, создайте статью, убедитесь, что в `jobs` есть задание, потом запустите `queue:work`.

```bash
php artisan queue:failed
php artisan test
```

Секреты хранятся только в локальном `.env`; `database.sqlite`, `LOCAL_LOGIN.txt`, `vendor` и логи исключены из Git. Повторная установка **не удаляет** новости.

## Хостинговая версия

Ветка `hosting-laravel13` использует MySQL InfinityFree и отдельный `.env.example` без паролей. Перед загрузкой нужны подготовленные Composer-зависимости, настройки базы и почты. Из-за ограничений бесплатного хостинга указывать `QUEUE_CONNECTION=database` **нельзя, если worker не запущен**, иначе письма навсегда останутся в очереди. Для сайта используем `sync`; для демонстрации именно фоновой очереди предназначена `main`.

## Лабораторная работа №11 — широковещание (Pusher + Laravel Echo + Vue)

При публикации статьи сервер создаёт событие \`App\Events\NewArticleEvent\`, реализующее \`ShouldBroadcast\`. Оно вещает в **публичный** \`Channel('articles')\` под именем \`NewArticleEvent\`. \`broadcastWith()\` передаёт \`article.id\`, \`article.title\` и внутреннюю ссылку \`article.url\`. Черновики не отправляются; если черновик впервые опубликован, событие тоже передаётся. Отправка почты через \`VeryLongJob\` из №10 остаётся без изменений.

Фронтенд: \`resources/js/components/App.vue\` показывает розовое всплывающее уведомление; \`resources/js/bootstrap.js\` создаёт клиент Pusher/Laravel Echo, слушатель подписан на \`articles\` и \`.NewArticleEvent\`. Сборка — через \`vite.config.js\`, \`package.json\`, \`npm run build\`. Разметка Vue подключена в \`resources/views/layouts/app.blade.php\`.

### Как включить настоящие push-уведомления

1. Создайте приложение **Pusher Channels**, выберите кластер **eu**. Сохраните его **App ID, Key, Secret**. Без аккаунта Pusher готовая реализация не сможет доставить сообщение в браузер.
2. Скопируйте \`.env.example\` в собственный \`.env\`, укажите \`PUSHER_APP_ID\`, \`PUSHER_APP_KEY\`, \`PUSHER_APP_SECRET\`, \`PUSHER_APP_CLUSTER=eu\` и **\`BROADCAST_CONNECTION=pusher\`**. Для совместимости с заданием можно также указать \`BROADCAST_DRIVER=pusher\`. Секрет никогда не публикуется в Git или браузере.
3. Выполните \`php artisan config:clear\`. Для локальной разработки установите PHP/JS-пакеты: \`composer install\`, \`npm install\`. Для стабильной демонстрации соберите production JS через \`npm run build\`. Команда \`npm run watch\` доступна для разработки через Vite, но требует включённого dev-сервера.
4. **Локально:** оставьте \`QUEUE_CONNECTION=database\`, запустите \`php artisan serve\` и **отдельно** \`php artisan queue:work database --tries=3 --sleep=1\`. При изменении .env перезапустите worker. **InfinityFree:** оставьте \`QUEUE_CONNECTION=sync\`; никакого фонового процесса на сервере запускать не нужно.
5. Откройте сайт в одном окне браузера как посетитель, а во втором войдите модератором и опубликуйте новость. В первом окне должно появиться всплывающее уведомление со ссылкой. После отправки не следует закрывать вкладку посетителя.

**Где брать готовые сборки:** [GitHub Actions](https://github.com/alinakashafutdinova/Servernaya_web-razrabotka_10-15/actions) собирает отдельно ZIP для \`main\` (SQLite + \`vendor\` + \`public/build\`) и для \`hosting-laravel13\` (MySQL + \`vendor\` + \`public/build\`). Обычный GitHub Download ZIP не включает \`vendor\` и готовый JS; для него нужны Composer и npm.

**Технические ограничения:** InfinityFree не предоставляет WebSocket-сервер, но браузеры могут подключаться к **внешнему** Pusher. В хостинговой ветке отправка события происходит в режиме \`sync\`. Без ключей Pusher оставляйте \`BROADCAST_CONNECTION=log\` — остальной сайт будет работать, но онлайн-пушей не будет.

В Laravel 13 публичный канал не требует добавления устаревшего \`App\Providers\BroadcastServiceProvider\` в \`config/app.php\`. Основная конфигурация вещания находится в \`config/broadcasting.php\`, фронтенд собирает Vite. Автотесты проверяют контракт события, публичный канал, полезную нагрузку, публикацию черновика и сохранение очереди №10. Проверка фактической внешней доставки через Pusher требует действующих ключей.


## Лабораторная работа №12 — уведомления читателям о новых статьях

**Цель:** уведомлять зарегистрированных читателей о публикациях даже тогда, когда они не находятся на сайте; показывать непрочитанные сообщения в выпадающем меню и открывать статью с отметкой о прочтении.

- Таблица `notifications` уже создана в предыдущих лабораторных (миграция `2026_11_19_000004_create_notifications_table.php`). Повторная миграция **не нужна**: иначе возникнет ошибка «table already exists». Для Laravel 13 команда генерации новой миграции — `php artisan make:notifications-table`, но в данном проекте достаточно `php artisan migrate`.
- Создан `app/Notifications/NewArticleNotification.php`: конструктор получает ID и заголовок статьи, `via()` возвращает `['database']`, `toDatabase()` — `type`, `article_id`, `article_title`, `message`.
- `NewsController::notifyReaders()` после создания опубликованной статьи вызывает `Notification::send($readers, new NewArticleNotification(...))`. Получатели — зарегистрированные пользователи с ролью `reader`, исключая инициатора текущего запроса. Модераторы уведомления не получают. **Вход читателей в момент публикации не требуется.** Публикация ранее скрытого черновика тоже создаёт уведомление, но повторное редактирование уже опубликованной статьи — нет.
- В `resources/views/layouts/app.blade.php` создан пункт «Уведомления» с количеством непрочитанных записей и раскрывающимся списком. CSS: `public/css/notifications.css`.
- В `AccountController::openArticleNotification()` через защищённый маршрут `POST /account/notifications/{notification}/open` уведомление ищется только среди записей вошедшего читателя, отмечается как прочитанное (`markAsRead()`) и открывается статья. Форма использует CSRF; чужие записи и уведомления другого типа не подходят. Если статья скрыта/удалена, пользователь безопасно перенаправляется к новостям.
- Существующие уведомления о модерации комментариев сохраняются. В личном кабинете новый тип показывается отдельно.

**Проверка №12:** зарегистрируйте читателя, **выйдите из его аккаунта**, войдите модератором, опубликуйте новость (не черновик), затем вновь войдите как читатель. Откройте выпадающий список «Уведомления» и нажмите на название публикации. После перехода счётчик должен уменьшиться на один, а уведомление будет прочитанным. Это **database**-уведомление, для него Pusher не требуется.

Автоматические тесты: `tests/Feature/NewArticleNotificationTest.php`; в CI проверяются получатели, миграция, новая статья, черновики, навигация, `read_at`, защита чужих записей и совместимость с модерацией.

## Лабораторная работа №13 — кеширование новостей и комментариев

**Названия классов:** статьи уже обслуживаются контроллером `NewsController` (в задании он назван ArticleController), комментарии — `CommentController`. Сайт и старые маршруты сохранены.

1. В `.env.example` обоих окружений: `CACHE_DRIVER=database`, `CACHE_STORE=database`. В Laravel 13 используется `CACHE_STORE`; оба параметра записаны ради совместимости с заданием. `config/cache.php` поддерживает `database`.
2. Миграция `2026_11_19_000006_create_cache_table.php` создаёт `cache` и `cache_locks` в SQLite (локально) или MySQL (InfinityFree). Выполните `php artisan migrate --force`, **не** добавляйте повторно миграцию.
   - **Локальная версия:** `php scripts/setup-local.php` автоматически обновляет `CACHE_STORE` и `CACHE_DRIVER` также в ранее созданном `.env` (пароли и прочие настройки сохраняются), затем выполняет миграции.
   - **InfinityFree:** `.env` на хостинге **не обновится от изменений в GitHub**. Установите оба параметра в существующем `.env`. Если нет SSH и доступа к Artisan, импортируйте `deploy/infinityfree_lab13_cache.sql` через phpMyAdmin: SQL создаёт `cache`, `cache_locks` и регистрирует миграцию. Дополнительная инструкция: `HOSTING_LAB13_SETUP.md`.

3. `NewsController::index`: `Cache::remember(..., 10 минут, ...)` кеширует каждую страницу `/news?page=N` с учётом номера страницы и количества записей. Страницы независимы, пагинация остаётся рабочей.
4. `NewsController::store`: `Cache::forget('news.index.version')` немедленно делает недействительными **все** закешированные страницы пагинации. Старые ключи автоматически истекают через 10 минут. Записи новых статей и рассылка из №10–12 остаются рабочими.
5. `NewsController::show`: `Cache::rememberForever('news.show.<id>', ...)` кеширует атрибуты статьи и **только одобренные** комментарии с публичными именами авторов. Сначала выполняется авторизация, поэтому чужой черновик читателям не показывается. Список связанных новостей обновляется без кеша, чтобы видеть новые публикации.
6. `NewsController::update` и `destroy`: `Cache::flush()` очищает кеш после сохранения/удаления статьи, как указано в задании. **Внимание:** `flush()` очищает весь используемый кеш; на общедоступном хранилище с другими приложениями нужна изоляция.
7. В `CommentController::store/approve/reject` добавлен `Cache::forget('news.show.<id>')`. Это предотвращает «застывшие» комментарии после модерации, не нарушая очереди и уведомления.

**Почему в кеше массивы:** Laravel 13 по умолчанию ограничивает десериализацию PHP-объектов из кеша. Мы сохраняем простые данные и восстанавливаем модели при отображении, не отключая защиту. Логины, пароли и конфиденциальные пользовательские данные в кеш не попадают.

**Как проверить:** создайте 13 опубликованных статей; откройте `/news`, `/news?page=2` и статью с комментариями — в таблице `cache` появятся записи. Опубликуйте новость и убедитесь, что страницы 1 и 2 показывают актуальный список. Одобрите комментарий модератором и перезагрузите статью — текст появится сразу. Измените или удалите новость — `Cache::flush()` очистит устаревшие результаты. Для диагностики используется `php artisan cache:clear`.

**Автотесты:** `tests/Feature/NewsCacheTest.php` проверяет миграции, работу SQLite database-cache, раздельную пагинацию, `rememberForever`, `forget`, `flush`, модерацию и доступ к черновикам.

## Лабораторная работа №14 — планировщик и статистика

**Цель:** сохранять запросы просмотра статей и отправлять модераторам ежедневное письмо о количестве просмотров и новых комментариев.

- **Модель и миграция:** `app/Models/ArticleView.php` и `2026_11_19_000007_create_article_views_table.php` создают `article_views` (article_id, url, viewed_at). Только успешные GET страницы `/news/{article}` фиксируются посредником `TrackArticleView`. URL хранится без query-string, IP и cookie, а несуществующие и чужие черновики не учитываются.
- **Middleware:** алиас `article.view` зарегистрирован в `bootstrap/app.php` и подключён к маршруту `news.show`. В Laravel 13 не нужно создавать старый `app/Http/Kernel.php`, потому что middleware настраиваются в `bootstrap/app.php`.
- **Команда:** `app/Console/Commands/SendDailyStatistics.php`, Artisan `stats:daily`. Подсчитывает просмотры и комментарии, остающиеся в базе, за выбранные сутки по часовому поясу `Europe/Moscow`.
- **Письмо:** `DailyStatisticsMail` и шаблон `resources/views/emails/daily-statistics.blade.php`. Получатели — только модераторы; таблица `daily_report_deliveries` (`2026_11_19_000008_create_daily_report_deliveries_table.php`) предотвращает повторную рассылку за одну дату и сохраняет успешную отправку каждому модератору.
- **Планировщик:** `routes/console.php` содержит `Schedule::command('stats:daily')->everyMinute()->withoutOverlapping(10)`. В учебном локальном режиме `DAILY_REPORT_DEMO_EVERY_MINUTE=true` первая проверка за день отправляет письмо; дальнейшие минутные запуски пропускают повторы. При `false` отчёт создаётся в 23:59 по Москве, если работает внешний cron. Команды: `php artisan schedule:list`, `php artisan schedule:run`, `php artisan schedule:work`.
- **Ручная проверка:** `php artisan stats:daily --force` отправит письмо повторно. В панели `/management` добавлена защищённая от посторонних и CSRF кнопка «Отправить статистику за сегодня» (не отправляет повторно уже отправленный отчёт).
- **Реальная почта:** `MAIL_MAILER=log` выводит письмо в `storage/logs/laravel.log`, но не доставляет во входящие. Для отправки в почтовый ящик настроить SMTP в личном `.env`.
- **Хостинг:** бесплатный InfinityFree **не поддерживает cron, SSH и внешние web-cron**. На нём работает учёт просмотров и ручная отправка письма модератором, но автоматическую рассылку без иной среды честно не гарантируем. Для MySQL использовать `deploy/infinityfree_lab14_views_reports.sql` через phpMyAdmin; подробности в `HOSTING_LAB14_SETUP.md`.

**Тестирование:** `tests/Feature/DailyStatisticsTest.php` проверяет подсчёт просмотров и комментариев, права доступа, отправку модераторам, даты, отсутствие дублей и расписание. В локальных скриптах запуска `schedule:work` стартует вместе с сайтом.
